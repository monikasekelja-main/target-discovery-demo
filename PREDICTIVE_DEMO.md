# Patient-study demo: stages A and B

This separate copy adds a proposed psoriasis patient scRNA study to the existing workbench. It is an offline workflow demonstration, not an executed prediction or evidence of biological efficacy. There is no patient dataset, selected model, real target ID or compute submission. No original reports were regenerated.

## Run and rehearse

Follow README installation instructions, then run `python -m streamlit run streamlit_app.py`. The default is Patient-study demo; an explicit TARGET_DEMO_WORKSPACE environment variable still opens the full workbench.

1. **Define the study:** inspect the scientific question, data requirements and reference population. The accession is intentionally absent and all donor identifiers are illustrative.
2. **Test the prediction:** distinguish patient-data adaptation from intended-use validation. Expand the activity record for checks, findings, actions and accountable owners.
3. **Review the experiment:** inspect the proposal and Who does what explanation. The analyst/challenger text is scripted, not generated by a model. Optionally rehearse APPROVE_SCOPED_TEST or DEFER with a rationale. This uses browser-session state only and performs no semantic AI check.
4. **Agree the next action:** inspect the chosen biology route, proposed measurements, specialist questions and expected interpretation of future results. No message, experiment or resource commitment is submitted.

Select a scenario and route in the top expander. Try missing annotation or a timeout: prediction stops, but independently justified parallel biology can still be considered. Try the resource-gap scenario: the prediction is supportive but neither route supports approval. A scope, input or route change creates a different review binding, so a review from another proposal is not displayed as current.

Session reviews disappear when the session ends. Returning to the exact same proposal can reuse its matching session review. They are not persistent workflow records. The downloaded nomination contains the illustrative evidence boundary, scenario, activity and binding; it is not an approved handoff.

## Evidence and approval boundaries

- Published disease background remains in the existing programme-context asset. It is not target-specific support for DEMO-R1.
- The study manifest and every scenario result are explicitly illustrative. Scenario checks that pass are assumptions in that scenario, not measured model performance.
- Model token deletion, partial transcript reduction, protein inhibition and receptor blockade are not interchangeable.
- An embedding shift does not predict an IL-17A percentage or establish therapeutic benefit.
- Hold out donors before data-dependent learning. Donor robustness does not prove intervention accuracy; claims of unseen-target transfer require an appropriate separate evaluation.
- Patient skin and stimulated CD4 culture are distinct contexts. Selective producer loss, reduced production and mixed mechanisms remain unresolved possibilities.
- Hypothesised differentiation, safety, specificity and clinical benefit remain untested.
- After-prediction approval requires a supportive nomination derived from the illustrative observations. Both routes require separate scientific-rationale, assay-readiness, decision-value and resource records. Parallel approval additionally requires its independent fictional evidence basis, which does not assert a patient-cell nomination. Both are rehearsal proposals requiring actual biology and resource-owner approval outside this demo.

## Implementation

`target_discovery/predictive/contracts.py` provides strict versioned Pydantic records. `replay.py` is a pure evaluator with explicit statuses, bounded simulated failure events and review binding. It contains no model adapter, network client, job submission or persistent write. A real-execution entry point fails closed.

`predictive_examples/study.json` contains the proposed study and illustrative manifest; `scenarios.json` covers supportive, inconclusive, annotation gap, influential donor, contradictory evidence, timeout, unvalidated intended use, unsupported perturbation and missing parallel prerequisites.

`target_discovery/ui/predictive_demo.py` renders the new journey. `ui/app.py` adds it as a new experience. The original guided renderer, calculations, tool registry, prompts and saved data remain unchanged. Existing guided tests explicitly select the preserved experience.

## Audit fixes: evidence to decision

The nomination-v2 contract carries per-state comparisons, separate prerequisites, contextual requests, independent parallel rationale, and a linked scripted specialist exchange. Every comparison comes from invented donor-level records rather than a preassigned supportive flag. The rule requires each held-out donor to exceed both the simple baseline and control, preserves identity, and ranks eligible states by mean shift. It is an illustrative rule, not a validated biological threshold. Leave-one-out means reveal donor dependence. Missing annotations, unsupported operation and timeouts provide no predictive results or nomination. Exploratory, inconclusive and conflicting results also produce no supported nomination.

Four development and four evaluation donor IDs are explicit in the illustrative study; overlapping splits block prediction. No invented values are borrowed from the independent assay backup. The mock representation scores do not estimate dose, cytokine response, cell survival or clinical benefit.

The specialist exchange is an offline example linked into the proposal record. Selecting **Include specialist recommendation in proposal** changes its scope and binding, making any earlier rehearsal approval inapplicable. The revised scope persists when returning to step 3. A deferred review stays yellow and its concern becomes the immediate next action.

Rationale text receives only a minimum-length completeness check. A prominent warning and scripted weak-rationale/guidance example make this limitation explicit; no semantic judgement is claimed. The optional AI check in the original workbench is preserved but is not called by this journey.

## Orchestrator, verifier and offline questions

Step 3 includes a compact control panel and a four-part trace derived from the current proposal. Orchestration routes the next permitted action; deterministic verification checks prerequisites and evidence comparisons; human reviewers approve scientific scope and resources. This is a replay, not a live LLM orchestration log, and fixed checks do not establish scientific truth.

**Ask about this proposal** is available on all four steps. Five predefined questions cover the next action, orchestrator/verifier roles, human judgement, parallel biology and the assistant boundary. Answers are fixed templates populated from the current study, scenario, route, specialist revision and matching session review. Sources and the exact proposal binding are expandable. No prior answer is cached across proposal changes. In offline mode, unknown questions are rejected by the helper; no API is called.

The offline explainer has no model, search, execution, editing, approval or messaging capability and never loads the original assay assessment. The original workbench evidence assistant remains separate and unchanged.

## Optional live proposal chat

In **Ask about this proposal**, offline examples remain the default. Select **Live assistant (API)** for free-text questions. The assistant receives only the current synthetic study, proposal, matching session review and up to three recent exchanges. Changing that context clears the conversation; history is session-only and can be cleared explicitly. No original assay assessment is injected.

Set `OPENAI_API_KEY` in the environment of the Streamlit process and restart it. Never enter the key in a question or commit it. Set `TARGET_PROPOSAL_MODEL` to a Responses model available to your API account; it falls back to `TARGET_REVIEW_MODEL` and the workbench default. The form also permits selecting a model. Missing credentials disable submission.

Each explicit submission makes one paid Responses request, with `store=false`, a 2,400-output-token cap, a 45-second request timeout and no automatic retries. There are no search, execution, editing, approval or messaging tools. This does not run the patient study or convert the illustrative orchestrator trace into a live scientific workflow.

Structured answers must include exact excerpts from supplied sources. Schema and excerpt checks reject malformed or ungrounded citations; they do not prove that an interpretation is scientifically correct. Model quality and applicability require human review. API errors are displayed without raw responses or credentials.

Live proposal answers use plain-language explanations aimed at scientific decision-makers. Internal status codes and source labels belong outside the main explanation; structured citations remain in the expandable source section with readable labels. Necessary scientific terms should be explained without weakening evidence boundaries. The prompt version changes the conversation binding so earlier wording is not reused as history.
